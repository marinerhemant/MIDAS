# TOMO/src bug fixes, 2026-08-13

Found while porting this engine into `packages/midas_tomo`. All were fixed in
the package first, then back-ported here. **Verified numerically inert**: a
binary built from this fixed source is bitwise identical to one built from the
source as it stood before, on the packaging-parity test.

Each was survivable in a standalone binary and fatal, or silently wrong, when
the same code is called in-process — which is how they surfaced.

### 1. Uninitialised FFT plan handles (crash) — `tomo_gridrec.c`

`initFFTMemoryStructures()` nulled the FFT buffers but left
`backward_plan_1d` / `forward_plan_2d` uninitialised, while
`destroyFFTMemoryStructures()` destroyed both unconditionally. A worker thread
that never ran a transform of a given rank passed stack garbage to
`fftwf_destroy_plan()`.

Masked here because the crash lands at teardown, after the output is written —
a wrong exit code at worst. Trigger: a run whose shift count differs from the
previous one in the same process.

### 2. Wrong buffer freed on 2-D resize (latent) — `tomo_gridrec.c`

`fourn()`'s resize path called `fftwf_free(param->in_1d)` — the
*one*-dimensional buffer — leaking the old 2-D buffer and leaving `in_1d`
dangling. Unreachable today (needs a second, different 2-D size within one
`gridrecParams`), so no behaviour change.

### 3. No required-key validation (crash) — `tomo_utils.c`

`setGlobalOpts()` failed only when the parameter *file* could not be opened.
A file missing `detXdim` left the field as whatever was on the stack, and that
garbage reached the allocator. Now the required fields are initialised to
sentinels and validated, including that `dataFileName` actually opens.

### 4–7. Swallowed errors (silent wrong answers) — `tomo_init.c`, `tomo_utils.c`

Four places detected a failure, printed to stderr, and carried on returning
success:

* multi-shift path: `if (badRead == 1) return 0;` — **returned success** on a
  failed read, giving a silently empty reconstruction
* single-shift path: a failed slice was `continue`d past, leaving that slice's
  output uninitialised
* `createPlanFile()` was `void` and discarded `readSino`/`readRaw`'s status —
  and it performs the *first* read, so it is where a bad input is caught
* all four `writeRecon()` call sites did `if (rw == 1) continue;`, so a failed
  or truncated write produced a partial cube

All now record the failure and return non-zero.

**The pattern:** an operator watching a terminal sees the stderr message and
notices something is wrong, so nothing ever forced the status to propagate.
Every one of these was found by a test asserting that bad input *fails*, not
by reading the code.
